ForSys Agent

The ForSys greedy spatial heuristic for fuel-treatment and restoration planning, executed entirely as DuckDB SQL over an H3 hex grid on cloud parquet. No solver, no R runtime, no preprocessed adjacency table.

What ForSys is, and why this is possible

ForSys is the US Forest Service's spatial planning platform for landscape restoration and fuel management. It ingests management priorities, treatment thresholds and operational constraints, and returns ranked, spatially explicit project areas — "the areas of the landscape that should be targeted for treatment first."

The decisive design fact is that ForSys optimizes with "a relatively simple greedy spatial heuristic instead of more complicated mathematical programming approaches used in many other planning systems." That is what makes it portable to an architecture like ours. Mixed-integer programming would not be: it needs a solver process holding the entire problem in memory, and a branch-and-bound tree cannot be pushed down into a parquet scan. A greedy heuristic needs neither. Every stage of it is an aggregation or a graph expansion, and those are things a database does natively.

Two properties of an H3 hex grid make the port easier here than in ForSys itself:

  • Adjacency is free and analytic. ForSys's patch builder (Patchmax) must derive a stand adjacency graph from polygon topology. On H3, h3_grid_disk is the graph and h3_grid_distance is the metric — computed from the cell index, with no topology step and no stored edge list.
  • Hexagons are already a supported decision unit. ForSys selects "treatment units within the planning area, such as delineated forest stands or a standardized decision unit like hexagons." We use the second option, which is also this catalog's standard join key.

How the algorithm maps onto SQL

ForSys conceptSQL / H3 implementation
Treatment unit (stand) One H3 cell. Resolution 8 ≈ 182 acres ≈ 74 ha is the default; resolution 9 ≈ 26 acres for finer units.
Priority layer A CTE aggregating one dataset to h8, normalized to 0–1 with MAX(x) OVER () inside the planning area.
Objective weighting A weighted sum of the normalized priority columns. Re-running with different weights is the tradeoff analysis.
Treatment threshold A WHERE clause on the unit's own attributes. Patchmax's threshold = 't1 == 1' is literally a filter string.
Restricted / excluded area An anti-join: h8 NOT IN (SELECT h8 FROM no_mech), built from the PAD-US combined layer.
Stand adjacency graph h3_grid_disk(cell, 1) — computed, never stored.
Contiguous project area A k-ring around a seed: h3_grid_disk(seed, k). k=1 → 7 cells, k=2 → 19, k=3 → 37.
area_max constraint The choice of k. At resolution 8, k=2 → 19 × 182 ≈ 3,460 acres.
Seed search ("score each stand as a potential seed") A moving-window aggregation: CROSS JOIN UNNEST(h3_grid_disk(seed, k)) then GROUP BY seed. Every candidate scored in one pass.
Constraint violation stops patch growth HAVING COUNT(*) = <ring size> — rejects any project area containing an ineligible cell.
Sequential project selection, excluding already-claimed stands Recursive CTE carrying claimed seeds as a list; reject candidates within 2k grid steps.
Project prioritization map / ranked plan The recursion's iteration number is the project rank.

Specifying the planning area

Every stage below operates on a units table of (h8, h0) rows, so the only thing that changes between the three ways of setting a planning area is how that table is built. Nothing downstream is aware of the difference.

A. Name an existing polygon

The cheapest and most precise option, and the one to reach for first. There are no geometry operations at all — the reference dataset is already hex-indexed, so naming a polygon is a plain attribute filter. This is how the default Tahoe National Forest planning area is defined. 

units AS (   -- a national forest
  SELECT DISTINCT h8, h0
  FROM read_parquet('s3://public-padus/padus-4-1/fee/hex/h0=*/data_0.parquet')
  WHERE h0 IN (SELECT h0 FROM scope)
    AND Des_Tp = 'NF' AND Unit_Nm = 'Tahoe National Forest'
)

units AS (   -- a named subwatershed
  SELECT DISTINCT h8, h0
  FROM read_parquet('s3://public-usgs-wbd/wbd/hu12/hex/h0=*/data_0.parquet')
  WHERE h0 IN (SELECT h0 FROM scope) AND name = 'Fordyce Creek'
)

Many catalog datasets carry nameable polygons that work this way: PAD-US units (Unit_Nm), HUC12 and HUC10 subwatersheds (name, huc12), counties, census places, congressional districts and ecoregions. The HUC12 layer ships in the layer menu as an outline overlay so subwatersheds can be read off the map and named directly. Within Tahoe National Forest they run roughly 28,000–33,000 acres each — a realistic project-planning extent:

B. A drawn polygon

The polygon draw tool is enabled, and the agent reads the geometry through its get_drawn_region tool. h3_polygon_wkt_to_cells converts it to treatment units. Note that h0 comes from the cells themselves — this replaces the usual scope CTE, and omitting it defeats partition pruning on every join that follows. 

units AS (
  SELECT h8, h3_cell_to_parent(h8, 0) AS h0
  FROM (SELECT UNNEST(h3_polygon_wkt_to_cells('POLYGON((...))', 8)) AS h8)
)

C. An uploaded GeoJSON

GeoJSON upload is enabled, accepting Polygon and MultiPolygon features. The file goes browser → S3 directly; only the resulting URL reaches the agent, via get_uploaded_dataset. DuckDB then reads it straight over HTTPS, with ST_Union_Agg collapsing a multi-feature file into a single area of interest. 

units AS (
  WITH aoi AS (SELECT ST_Union_Agg(geom) AS g FROM ST_Read('https://…/uploads/aoi.geojson'))
  SELECT h8, h3_cell_to_parent(h8, 0) AS h0
  FROM (SELECT UNNEST(h3_polygon_wkt_to_cells(ST_AsText((SELECT g FROM aoi)), 8)) AS h8)
)

A drawn or uploaded polygon is not automatically treatable land. A box dragged over Tahoe National Forest also covers private parcels, reservoir surface and land outside the forest boundary. The next section gives the PAD-US screen that turns an arbitrary polygon into treatable land. Path A largely avoids the problem, which is part of why it is preferred.

Ownership and protection status — the PAD-US screen

PAD-US answers both "who owns this" and "what treatment is permissible", which is how any area of interest becomes treatable land. GAP status is the operative field, because it encodes the disturbance regime rather than just the ownership:

GAPMeaningTreatment implication
3 Permanent protection, multiple use, extractive use (logging, OHV) permitted The focal candidates. National forests are here — Tahoe NF is uniformly GAP 3.
2 Biodiversity primary, natural disturbance suppressed Fuels accumulate precisely because fire is suppressed — ecologically interesting — but these are usually another owner's conservation lands, so mechanical treatment is not a Forest Service action. Excluded by default.
1 Biodiversity primary, natural disturbance proceeds or is mimicked Fire is allowed to do the work. Designated wilderness lives here. Not a mechanical-treatment candidate.
4 No known mandate for biodiversity protection Mixed; screen case by case.
absent Not in PAD-US at all Almost always private land, plus some DoD installations. Not a federal treatment candidate — identified by an anti-join against PAD-US.

This is the concrete answer for a drawn or uploaded polygon: join the area of interest to PAD-US on h8 AND h0 and keep GAP 3, optionally narrowing Mang_Name to the agency in question. Cells with no PAD-US match are private. The split — federal multi-use versus protected versus private — should be reported before any acreage is quoted.

Screen protection status on the combined layer, never on fee. Designations overlay fee ownership and are absent from the fee layer. Granite Chief Wilderness — GAP 1, Des_Tp = 'WA', IUCN Ib, ~27,000 acres — lies inside the Tahoe National Forest boundary but appears only in combined. An earlier version of this app screened on fee, which meant the exclusion matched zero cells and the algorithm was free to site mechanical treatment inside designated wilderness. Fixing it to combined removed 569 cells and dropped one project area from the top eight — the one containing the Royal Gorge and Chickering American River Reserve preserves.

Stage 1 — Scope the partitions

Every hex dataset in the catalog is hive-partitioned by h0 (H3 resolution 0). Establishing the h0 set first, and carrying it into every subsequent join, is what keeps the query from opening every partition file on S3. This is the single largest performance lever in this architecture — an order of magnitude, not a few percent. 

WITH RECURSIVE scope AS (
  SELECT DISTINCT UNNEST(h3_grid_disk(h3_latlng_to_cell(lat, lng, 0), 1)) AS h0
  FROM (VALUES (39.3,-120.5),(39.5,-121.0),(39.0,-120.2)) AS t(lat,lng)
)

Every join between two hex datasets must include h0: ON a.h8 = b.h8 AND a.h0 = b.h0. With h0 in the join condition, DuckDB's dynamic partition pruning matches it against the hive partition path and skips non-matching files before reading them. Join on h8 alone and it can only use row-group statistics, which requires opening every file for a footer read — roughly 100 ms each over HTTP.

Stage 2 — Treatment units

The planning area becomes one row per H3 cell. DISTINCT matters: PAD-US features overlap, so a cell can appear more than once. 

units AS (
  SELECT DISTINCT h8, h0
  FROM read_parquet('s3://public-padus/padus-4-1/fee/hex/h0=*/data_0.parquet')
  WHERE h0 IN (SELECT h0 FROM scope)
    AND Des_Tp = 'NF' AND Unit_Nm = 'Tahoe National Forest'
)

Stage 3 — Priorities

Each management objective becomes one CTE aggregating a dataset to h8. Three are wired up by default, and each illustrates a different aggregation discipline.

Fuel hazard — fractional coverage

Conifer share of mapped area, from the CWHR 13-class habitat product. The fractions asset carries one (class, frac) row per class present in each cell, so composition is exact and mass-conserving. The companion mode asset collapses each cell to its dominant class and biases per-class area in both directions — it is for map styling, not for area. 

fuel AS (
  SELECT c.h8,
         SUM(CASE WHEN c.whr13num IN (31,32) THEN c.frac ELSE 0 END)
           / NULLIF(SUM(c.frac), 0) AS conifer_frac
  FROM units u
  JOIN read_parquet('s3://public-ca30x30/cwhr13/hex-fractions/h0=*/data_0.parquet') c
    ON c.h8 = u.h8 AND c.h0 = u.h0
  GROUP BY c.h8
)

Irrecoverable carbon — raster hex, safe to SUM

The carbon hex is raster-derived: exactly one row per resolution-9 cell, holding a total in Mg C already area-integrated from the source density. Summing it up to h8 is directly valid, with no deduplication. 

carbon AS (
  SELECT k.h8, SUM(k.carbon) AS carbon_mg
  FROM units u
  JOIN read_parquet('s3://public-carbon/irrecoverable-carbon-2024/hex/h0=*/data_0.parquet') k
    ON k.h8 = u.h8 AND k.h0 = u.h0
  GROUP BY k.h8
)

Community exposure — the moving window

This is the stage that most needs H3. A treatment unit's value for community protection depends on what is near it, not what is in it: national-forest cells are overwhelmingly uninhabited, so a per-cell housing measure would score the entire planning area at zero. "Exposure within k rings" is a self-join over h3_grid_disk — a moving-window aggregation, entirely set-at-a-time. 

wui AS (
  SELECT h8, AVG(HUDEN2020) AS hu_den
  FROM read_parquet('s3://public-wui/wui-2020/hex/h0=*/data_0.parquet')
  WHERE h0 IN (SELECT h0 FROM scope) AND STATE = 'CA'
  GROUP BY h8
),
exposure AS (
  SELECT u.h8, COALESCE(MAX(w.hu_den), 0) AS nbr_hu_den
  FROM units u
  CROSS JOIN UNNEST(h3_grid_disk(u.h8, 5)) AS r(nb)   -- ~4.6 km at res 8
  LEFT JOIN wui w ON w.h8 = r.nb
  GROUP BY u.h8
)

Why HUDEN2020 and not HU2020. On a vector hex asset, per-feature totals are repeated on every cell the feature covers — a census block spanning 40 cells writes its housing count 40 times. Summing that inflates the answer. HUDEN2020 is a density, so averaging and taking a maximum are both safe with no _cng_fid deduplication. Prefer a density or a fraction column whenever one exists.

Stage 4 — Thresholds, exclusions, weighted score

Thresholds screen units on their own attributes; exclusions are anti-joins. Normalization uses MAX(...) OVER () so the 0–1 range is relative to this planning area — normalizing against a global maximum would flatten every score toward zero. Housing density gets a ln(1 + x) transform because it spans four orders of magnitude and would otherwise let one dense block dominate the objective. 

avail AS (
  SELECT u.h8,
         0.40 * (ln(1 + e.nbr_hu_den) / MAX(ln(1 + e.nbr_hu_den)) OVER ())
       + 0.35 * f.conifer_frac
       + 0.25 * (c.carbon_mg / MAX(c.carbon_mg) OVER ()) AS score
  FROM units u
  JOIN fuel f     ON f.h8 = u.h8
  JOIN exposure e ON e.h8 = u.h8
  LEFT JOIN carbon c ON c.h8 = u.h8
  WHERE f.conifer_frac >= 0.25                          -- treatment threshold
    AND u.h8 NOT IN (SELECT h8 FROM no_mech)            -- GAP 1/2 + wilderness
    AND u.h8 NOT IN (SELECT h8 FROM burned)             -- exclusion
)

The two exclusions are ordinary scans reduced to a bare list of cells:

no_mech AS (      -- COMBINED layer: designations overlay fee ownership
  SELECT DISTINCT h8 FROM read_parquet('s3://public-padus/padus-4-1/combined/hex/h0=*/data_0.parquet')
  WHERE h0 IN (SELECT h0 FROM scope)
    AND (GAP_Sts IN ('1','2') OR IUCN_Cat IN ('Ia','Ib') OR Des_Tp IN ('WA','SW','RNA'))
),
burned AS (       -- recently burned: fuels already reduced
  SELECT DISTINCT h8 FROM read_parquet('s3://public-fire/calfire-2025/firep/hex/h0=*/data_0.parquet')
  WHERE h0 IN (SELECT h0 FROM scope) AND YEAR_ >= 2015
)

Stage 5 — Seed scoring

Patchmax evaluates each stand as a potential seed, reporting "the potential objective score of a patch if it were built from that location," and describes this as working like a moving window. That is exactly a neighborhood aggregation, so all candidate seeds are scored in a single pass rather than one search per seed.

HAVING COUNT(*) = 19 does real constraint work: a k=2 ring has 19 cells, so a seed only survives if all 19 are eligible. Any project area that would reach into GAP 1/2 protection, a recent burn, sub-threshold vegetation, or off the forest is rejected whole. 

patch AS (
  SELECT s.h8 AS seed, SUM(a.score) AS patch_score
  FROM avail s
  CROSS JOIN UNNEST(h3_grid_disk(s.h8, 2)) AS r(nb)
  JOIN avail a ON a.h8 = r.nb
  GROUP BY s.h8
  HAVING COUNT(*) = 19
)

Stage 6 — Greedy selection, in one statement

Patchmax builds projects sequentially, "excluding previously recorded stands from subsequent searches." With fixed-radius k-ring patches that exclusion has an exact closed form: two patches overlap if and only if their seeds are within 2k grid steps. So the greedy loop becomes — take the best-scoring seed, reject every seed within 2k, repeat.

A recursive CTE carrying the claimed seeds as a list expresses this without a client-side driver. The LATERAL subquery is what supplies the ORDER BY … LIMIT 1 that a recursive term cannot hold directly. 

step AS (
  SELECT 1 AS proj,
         (SELECT seed FROM patch ORDER BY patch_score DESC LIMIT 1) AS seed,
         [(SELECT seed FROM patch ORDER BY patch_score DESC LIMIT 1)] AS claimed
  UNION ALL
  SELECT s.proj + 1, nxt.seed, list_append(s.claimed, nxt.seed)
  FROM step s, LATERAL (
    SELECT p.seed FROM patch p
    WHERE NOT EXISTS (
      SELECT 1 FROM UNNEST(s.claimed) AS c(cs)
      WHERE h3_grid_distance(p.seed, cs) <= 4       -- 2k, k=2
    )
    ORDER BY p.patch_score DESC
    LIMIT 1
  ) nxt
  WHERE s.proj < 8
)
SELECT s.proj AS project_rank, round(p.patch_score, 2) AS patch_score,
       h3_cell_to_lat(s.seed) AS lat, h3_cell_to_lng(s.seed) AS lng
FROM step s JOIN patch p ON p.seed = s.seed
ORDER BY s.proj;

What this does not do

The honest limits matter more than the capability, so they are listed plainly.

  • No optimality guarantee. Greedy heuristics carry no bound — and neither does ForSys. These are defensible, reproducible priority orderings, not optima. Anything needing a provable optimum needs mixed-integer programming, which is genuinely out of scope for this architecture.
  • Compact patches only. Project areas here are k-rings. Patchmax grows irregular patches by Dijkstra-ordered expansion, which lets a project follow a ridgeline or a fuel break. That is expressible as a recursive cost-distance relaxation over the hex graph, but is not what this app does.
  • No treatment-response modelling. ForSys reports outcomes — flame-length reduction, biomass produced, habitat restored. Those need treatment-effect models and data this catalog does not hold. This app prioritizes where; it does not predict what treatment achieves.
  • Coarse operability screening. Real plans screen on slope, yarding distance and road access. Only vegetation, ownership and burn history are screened here.
  • Not a treatment prescription. Output is a prioritization score under user-chosen weights. A real plan requires field verification, NEPA review and local knowledge.
